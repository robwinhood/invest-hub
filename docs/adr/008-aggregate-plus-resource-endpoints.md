# ADR-008: 집계 엔드포인트 + 도메인별 리소스 엔드포인트 (하이브리드 API)

## 상태

확정 (2026-06-07)

## 맥락

기능 요구사항은 *"세 데이터 소스를 취합·가공하여 **최적의 단일 응답 스펙**을 제공"* 하라고 한다.
초기 구현은 이를 **단일 집계 엔드포인트** `GET /api/v1/investment/dashboard` 하나로만 제공했다.

그런데 설계 제약(나)을 다시 보면 단일 엔드포인트 *하나로만* 끝낼 때 다음이 충돌한다.

1. **데이터 속성별 최적화 충돌(제약 3)**: 한 응답에 실시간(주식)·저실시간(추천)·중간(자산)이 섞이면, 응답 전체의 캐시·신선도 정책이 **가장 휘발성 높은 데이터(주식) 기준**으로 강제된다. 추천(5분 캐시 가능)에 HTTP `Cache-Control`/ETag를 걸 수 없다.
2. **자원 효율 충돌(제약 2)**: 모바일에서 "주식만 새로고침" 해도 집계는 **자산·추천까지 전부 재조회**한다. 100K TPS에서 불필요한 원본 호출·대역폭 낭비.
3. **독립성 충돌(제약 1)**: 세 도메인의 갱신·실패·캐싱 생명주기가 HTTP 경계에서 강제로 결합된다.

즉 우리가 내부(CB·L1/L2 캐시)에서 한 "데이터 속성별 처리"가 **API 경계까지 확장되지 못하는** 약점이 있었다.

> 참고: "단일 응답 스펙"은 *"엔드포인트가 정확히 1개"* 보다 **"취합·가공된 일관된 응답 스펙(스키마)을 제공"** 으로 읽는다. 같은 요구사항이 "엔드포인트**와** 데이터 구조를 자유롭게 디자인"하라고도 명시한다.

## 결정

**집계(BFF) 엔드포인트는 첫 화면용으로 유지하고, 도메인별 단독 리소스 엔드포인트를 추가하는 하이브리드**로 간다.

| 엔드포인트 | 용도 | HTTP 캐시 정책 (데이터 속성 반영) |
|---|---|---|
| `GET /dashboard` | **첫 진입 1회 렌더(집계)** — 3소스 병렬 조합, Partial Success | `no-store` (실시간 포함) |
| `GET /assets` | 내 계좌/자산 단독 | `private, max-age=30` (사용자별·저빈도 변경) |
| `GET /foreign-stocks` | 해외 주식 단독 (실시간 polling) | `no-store` (실시간 필수) |
| `GET /recommendations` | 추천 단독 | `private, max-age=300` (L2 TTL과 정렬) |

- 도메인 단독 엔드포인트는 부분 실패를 **상태 코드**로 표현한다: `CIRCUIT_OPEN/SERVICE_UNAVAILABLE→503`, `TIMEOUT→504`, `RESOURCE_EXHAUSTED→429` (`SectionHttpStatus.kt`). 클라이언트가 backoff·재시도 여부를 코드만으로 판단.
- 집계 엔드포인트는 기존대로 **200 + 섹션 `status=FAILURE`** (부분 실패 시에도 정상 섹션은 보여야 하므로).

### 중복 제거 — 하나의 서비스, 네 유스케이스

`InvestmentDashboardService`가 입력 유스케이스 4개를 모두 구현한다: 도메인별 3개(`GetAssetSummaryUseCase`·`GetForeignStockPortfolioUseCase`·`GetRecommendedProductsUseCase`) + 집계 1개(`GetInvestmentDashboardUseCase`). **집계는 도메인 유스케이스를 병렬로 재사용**하므로 조회·실패 분류 로직이 한 곳에만 존재한다. 컨트롤러는 얇다.

## 이유

- **데이터 속성별 최적화를 API 경계까지 확장**(제약 3): 내부 캐시 TTL을 HTTP `Cache-Control`과 정렬했다.
  - 단, 추천·자산은 사용자별이라 `private`(공유 캐시 금지) → **클라이언트 측 재조회 감소**가 효과다. 교차 사용자 원본 offload는 서버의 **L1+L2 캐시**가 담당한다(두 계층이 각자 역할).
- **독립 갱신·실패**(제약 1·2): 주식만 새로고침 = 주식만 호출. 한 도메인 장애가 다른 엔드포인트에 영향 0.
- **모바일 효율**: 첫 로딩은 집계 1회로 RTT 최소화, 이후 갱신은 도메인별. 과도 분할로 첫 화면을 N번 호출하게 만들지 않는다.

## 대안 및 기각

- **집계 단일 엔드포인트만**: 위 제약 충돌로 기각(데이터 속성별 캐시 불가).
- **도메인별 엔드포인트만(집계 없음)**: 첫 화면에서 3회 호출 → 모바일 RTT·렌더 지연 악화로 기각.
- **GraphQL**: 필드 선택 유연성은 좋으나 과제 범위·캐시 정책 제어·러닝커브 대비 과함. REST 하이브리드가 적합.

## 결과

- 새 데이터 소스 추가 시: 도메인 입력 유스케이스 + 얇은 리소스 컨트롤러(+속성별 `Cache-Control`)를 함께 추가하고, 집계 서비스가 이를 재사용하도록 한다.
- 집계 응답은 `no-store`, 캐시 가능한 데이터는 단독 엔드포인트에서만 캐시한다.
