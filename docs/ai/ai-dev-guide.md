# AI 자동 개발·운영 활용 가이드

> **대상**: 이 프로젝트에서 AI(Claude Code)를 주 개발자로 사용하는 모든 팀원
>
> **핵심 원칙**: AI가 개발한다 → CI가 자동으로 검증한다 → 사람은 PR만 리뷰하고 배포를 결정한다

---

## 한눈에 보는 전체 흐름

```
[사람]                    [AI]                      [자동화]
  │                        │                            │
  ├─ PRD 작성 ────────────>│                            │
  │                        ├─ 코드 생성                 │
  │                        ├─ 테스트 작성               │
  │                        ├─ ./gradlew test 실행 ─────>│ (로컬 검증)
  │                        ├─ PR 생성                   │
  │                        │                            ├─ CI 자동 실행
  │                        │                            │  (GitHub Actions)
  ├─ PR 리뷰 <─────────────────────────────────────────┤
  ├─ Merge 결정            │                            │
  └─ 배포 결정             │                            │
```

## 시나리오 1: 새 기능 추가 (새 데이터 소스)

### 사람이 할 일 (5분)

**1단계: PRD 채우기**

`docs/template/prd-datasource-template.md`를 열어 양식을 복사한다.
데이터 소스 이름, 필드, 실시간성, Mock 데이터를 채운다.

**2단계: Claude Code에 입력**

```
/add-datasource

[채운 PRD 내용 붙여넣기]
```

**3단계: AI가 만든 PR 리뷰**

AI가 코드를 생성하고 테스트를 돌린 뒤 PR을 만들면,
`.github/pull_request_template.md`의 체크리스트를 확인한다.

체크리스트 항목이 모두 초록불이면 Merge한다.

> 한 번에: `/ship`에 PRD를 그대로 주면 `add-datasource`(③)부터 자가검토·검증·PR 생성까지 묶어서 처리한다. (시나리오 5 참고)

### AI가 자동으로 하는 일 (사람 개입 없음)

| AI가 만드는 파일 | 역할 |
|---|---|
| `domain/{이름}/` | 데이터 구조 정의 + 입력값 자동 검증 |
| `application/port/output/` | 연결 인터페이스 (Out-Port) |
| `application/port/input/Get{이름}UseCase` | 도메인 단독 조회 유스케이스 (입력 포트) |
| `adapter/out/{이름}/` | 실제 외부 시스템 연동 (현재는 Mock) |
| `application.yml` 항목 추가 | 장애 대응 설정 (차단기, 격벽, 타이머) |
| `InvestmentDashboard.kt` 수정 | 응답 구조에 새 섹션 추가 |
| `InvestmentDashboardService.kt` 수정 | 유스케이스 구현 + 집계 병렬 재사용 |
| `InvestmentDashboardResponse.kt` 수정 | JSON 응답 필드 추가 |
| `{이름}Controller` 추가 | 도메인 단독 엔드포인트 + 속성별 Cache-Control (ADR-008) |
| 테스트 추가 | 정상/실패/부분실패 + 리소스 엔드포인트(상태·캐시) 검증 |

## 시나리오 5: PRD에서 PR까지 한 번에 (`/ship`)

`/ship`은 **전체 개발 파이프라인**을 끝까지 끌고 간다. PRD만 주면 요구사항 분석 → 설계 → 개발+테스트 → 자가검토 → PR 생성까지 자동으로 흐른다. **적응형**이라 이미 끝난 단계는 건너뛴다(코드가 다 됐으면 마무리만).

```
# 요구사항(PRD)을 주면 — 전체 파이프라인
/ship 국내 ETF 포트폴리오 섹션 추가 (저실시간, 캐시 10분). PRD: docs/prd-etf.md

# 코드가 이미 다 됐으면 — 마무리(자가검토→PR)만
/ship
```

`/ship`이 적응형으로 수행한다: **①요구사항 분석 → ②설계(필요 시 ADR) → ③개발+테스트 → ④자가검토 → `./gradlew check-all` → 커밋 → 푸시 → ⑤PR 생성**.
PR 본문에는 체크리스트와 자가 검토 보고서가 이미 채워져 있어, 사람은 **리뷰·승인·머지**(⑤의 본질)만 하면 된다.

| 쓰는 법 | 결과 |
|---|---|
| `/ship <PRD/요구사항/이슈>` | 요구사항 분석부터 전체 파이프라인 → PR 생성 |
| `/ship` (코드 작성 완료 상태) | 자가검토 → 검증 → 커밋·푸시 → PR 생성 (마무리 모드) |
| `/ship ... 머지까지 해줘` | 위 + CI 통과 확인 후 자동 머지 |

**주의**: `main`/`develop`이면 `/ship`이 커밋 전에 피처 브랜치를 따로 만든다(보호 브랜치 직접 커밋 금지).
최초 1회 `gh auth login`(GitHub 로그인)이 되어 있어야 한다. `check-all` 실패 시 PR을 만들지 않고 멈춘다.

## 자동화 안전망 — AI가 실수해도 잡히는 구조

### 레벨 1: 코드 작성 시 (즉시)

- **도메인 `require()`**: 음수 잔액, 빈 ID 등 비정상 값 → 객체 생성 시점에 예외
- **Kotlin 컴파일러**: 타입 오류, Sealed Class 분기 누락 → 컴파일 실패

### 레벨 2: 테스트 실행 시 (AI가 로컬에서 실행)

- **단위 테스트 129개**: 정상/실패/부분실패 시나리오 검증
- **ArchUnit 6개 규칙**: 아키텍처 경계·코루틴 금지·CB 누락 → 테스트 실패

### 레벨 3: PR 생성 시 (GitHub Actions 자동)

```yaml
# .github/workflows/ci.yml
# push/PR 때마다 자동으로 실행됨
./gradlew test  # 전체 테스트
./gradlew build # 빌드 검증
```

CI가 실패하면 PR에 빨간불이 뜬다. Merge 불가.

### 레벨 4: PR 리뷰 (사람)

`.github/pull_request_template.md` 체크리스트:
- 아키텍처 규칙 준수 여부
- MDC 래퍼 사용 여부
- 테스트 통과 여부
- CHANGELOG 업데이트 여부

모든 체크 → Merge → 배포 결정

## 사람이 절대 건너뛰면 안 되는 것

| 건너뛰면 안 되는 것 | 이유 |
|---|---|
| PR 체크리스트 확인 | AI가 `supplyAsyncWithMdc()` 대신 `supplyAsync()`를 쓰는 실수를 할 수 있다 |
| CI 통과 확인 | 로컬에서만 테스트하고 PR을 올리면 다른 환경에서 실패할 수 있다 |
| CHANGELOG 확인 | 무엇이 바뀌었는지 기록이 없으면 배포 후 장애 시 원인을 찾기 어렵다 |
| 배포 최종 결정 | 이것만 사람이 한다 |
