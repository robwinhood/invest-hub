# AI 개발 워크플로우 — 5단계 프로세스

> 이 프로젝트의 모든 기능 개발은 아래 5단계를 따른다.
> **1~4단계는 AI가 자동으로 수행**하고, **5단계(리뷰·머지)만 사람이 담당**한다.
> 목표: 사람의 리소스를 "판단과 승인"에만 집중시키고, 반복 작업은 AI에게 맡긴다.

---

## 전체 흐름 한눈에 보기

```
①  PRD          ②  설계         ③  개발+테스트     ④  비판적 검토    ⑤  사람 리뷰
요구사항 정의  →인리  방식 결정    →  코드+테스트 작성  →  자가 검토     →  승인·머지
─────────────    ──────────      ───────────────     ────────────     ──────────
사람(양식)      AI              AI                  AI               사람
+ AI 보조        (ADR 참조)      (skill)             (self-review)    (PR+CI)
═══════════════════════ AI 자동 구간 ═══════════════════════════    ══ 사람 ══
```

---

## 단계별 상세

### ① PRD — 요구사항 정의 (사람이 양식 작성, AI가 보조)

**무엇을**: "무엇을 만들지"를 구조화된 양식으로 적는다.

**어떻게**:
- 새 데이터 소스 추가 → `docs/template/prd-datasource-template.md` 양식을 채운다.
- 그 외 기능 → 자연어로 요구사항을 적되, "성공 조건"과 "실패 시 동작"을 명시한다.

**산출물**: 채워진 PRD (양식 또는 자연어)

> 사람이 하는 일은 여기서 거의 끝난다. 이후는 AI가 자동으로 흐른다.

---

### ② 설계 — 방식 결정 (AI)

**무엇을**: PRD를 이 프로젝트의 기존 원칙에 맞춰 어떻게 구현할지 결정한다.

**어떻게**: AI가 다음을 참조해 설계를 확정한다.
- `CLAUDE.md` — 절대 금지 사항, 기술 스택, 패키지 규칙
- `docs/adr/` — 기존 설계 결정 (왜 코루틴을 안 쓰는지 등)

**판단 기준**:
- 실시간 데이터인가, 저실시간인가? → `ResilientAdapter` vs `CachingResilientAdapter`
- 새로운 설계 결정이 필요한가? → 새 ADR 작성

**산출물**: 구현 방향 (필요 시 새 ADR)

---

### ③ 개발 + 테스트 (AI)

**무엇을**: 코드와 테스트를 함께 작성한다. 테스트 없는 코드는 미완성으로 본다.

**어떻게**:
- 새 데이터 소스 → `/add-datasource` skill에 PRD를 넣으면 약 10개 파일(도메인·포트·어댑터·설정·Sealed Result·서비스·응답 DTO·**입력 유스케이스·도메인 리소스 컨트롤러**·테스트)이 자동 생성된다. (집계 + 도메인별 엔드포인트 모두, ADR-008)
- 그 외 → 헥사고날 레이어 순서(domain → port → service → adapter)로 작성하고 각 레이어 테스트를 동반한다.

**산출물**: 컴파일·동작하는 코드 + 테스트

---

### ④ 비판적 검토 — 자가 검토 (AI)

**무엇을**: "동작하니까 됐다"가 아니라 "원칙과 안전 기준에 맞는가"를 AI가 스스로 점검한다.

**어떻게**: `/self-review` skill을 실행한다. 체크리스트(안전성·아키텍처·휴먼 에러 방지·동시성·테스트·문서)를 하나씩 점검하고 위반 사항을 즉시 수정한다.

**산출물**:
- 발견·수정 항목 목록
- 의도적으로 남긴 한계 + 이유 (사람이 판단하도록)
- `check-all` 통과 결과

> 이 단계가 사람 리뷰의 품질을 결정한다. AI가 기계적으로 잡을 수 있는 것은 여기서 다 잡고,
> 사람에게는 "판단이 필요한 것"만 넘긴다.

---

### ⑤ 사람 리뷰 — 승인·머지 (사람)

**무엇을**: AI가 만든 결과물을 사람이 검토하고 머지를 결정한다.

**어떻게**:
1. `/ship`이 **②~⑤(PR 생성)의 AI 구간을 끝까지** 끌고 온다. PRD를 주면 ①요구사항 분석부터, 코드가 이미 됐으면 ④자가검토부터 — 적응형으로 남은 단계만 수행한 뒤 `check-all` → 커밋 → 푸시 → **PR 생성**까지 자동으로 끝낸다. PR에는 `.github/pull_request_template.md` 체크리스트와 자가 검토 보고서가 채워져 있다.
2. CI(`.github/workflows/ci.yml`)가 자동으로 `lintKotlin + test`를 돌린다. 실패 시 머지 불가.
3. 사람은 **④단계 자가 검토 보고서의 "의도적으로 남긴 항목"** 과 비즈니스 타당성에만 집중한다.
4. 승인 후 머지한다. **이 리뷰·승인·머지가 ⑤의 본질이며 사람의 몫이다.** ("머지까지 해줘"라고 지시한 경우에만 `/ship`이 CI 통과를 확인하고 자동 머지한다.)

**산출물**: 승인 → 머지 → 배포

---

## 각 단계를 지탱하는 자동화 장치

| 단계 | 장치 | 역할 |
|---|---|---|
| ① PRD | `docs/template/prd-datasource-template.md` | 요구사항 양식 |
| ② 설계 | `CLAUDE.md`, `docs/adr/` | AI가 따를 원칙·결정 기록 |
| ③ 개발 | `.claude/commands/add-datasource.md` | 약 10개 파일 자동 생성 skill (집계 + 도메인 엔드포인트) |
| ④ 검토 | `.claude/commands/self-review.md` | 비판적 자가 검토 skill |
| ④ 검토 | ArchUnit | 아키텍처·코루틴 금지·CB 누락 자동 차단 |
| ④ 검토 | Ktlint | 포맷·스타일 자동 강제 |
| ①분석~⑤PR | `.claude/commands/ship.md` (`/ship`) | PRD→요구사항분석→설계→개발+테스트→자가검토→check-all→커밋→푸시→PR 생성. **적응형**(이미 끝난 단계는 건너뜀). 리뷰·머지(⑤ 본질)는 사람 |
| ⑤ 리뷰 | `.github/pull_request_template.md` | 리뷰 체크리스트 |
| ⑤ 리뷰 | `.github/workflows/ci.yml` | CI 자동 검증 (머지 게이트) |

---

## 사람 리소스가 줄어드는 지점

| 전통적 방식 | 이 프로젝트 |
|---|---|
| 사람이 코드 작성 | AI가 작성 (③) |
| 사람이 테스트 작성 | AI가 동반 작성 (③) |
| 사람이 컨벤션·아키텍처 일일이 리뷰 | ArchUnit·Ktlint가 자동 차단 (④) |
| 사람이 "혹시 빠뜨린 것" 찾기 | `/self-review`가 체크리스트로 자동 점검 (④) |
| 사람이 빌드·테스트 수동 실행 | CI가 자동 (⑤) |
| **사람이 남는 일** | **비즈니스 타당성 판단 + 최종 승인 (⑤)** |

사람은 "AI가 구조적으로 잡을 수 없는 것"(비즈니스 판단, 한계 수용 여부)에만 시간을 쓴다.
